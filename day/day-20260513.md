```
implement the EasyPostTrackerStatusReader

Your three flags are not enough to mirror what Helios actually does with EasyPost, if the goal is to stay close to current behavior without re-parsing every scan.

Today the pipeline cares about these rollup concepts from EasyPost’s per-detail `status` (and special rules for the first `pre_transit` / first `in_transit`):

|EasyPost `status`|`STATUS_TO_EVENT_TYPE` / specials|Role|
|---|---|---|
|`pre_transit`|First → acknowledgement; later pre_transit uses `pre_transit` → unknown-ish branch|“Label / pre-shipment”|
|`in_transit`|First → acceptance; then `transit`|“In network” + acceptance milestone on first scan|
|`out_for_delivery`|`transit`|Last mile, not delivered|
|`delivered`|delivery|Terminal success|
|`available_for_pickup`|`transit`|Not delivered; pickup semantics|
|`return_to_sender`, `failure`, `error`|exception|Problem / return path|
|`cancelled`|exception|Shipment/tracking cancelled|

So:

- `is_delivered` — aligns with `delivered` and with “delivery” processing. Good.
- `is_cancelled` — only `cancelled` should set this. Good and distinct from “returned” or “failed”.
- `is_accepted` — in Helios, “acceptance” is not the same as EasyPost’s English word “accepted”. It is mostly “first `in_transit` scan is forced to `acceptance` event type” plus any detail whose mapped `event_type` is acceptance. Aggregate `tracker.status` is often still `in_transit` long before/after that nuance. So if `TrackerStatus` is computed only from aggregate `status`, `is_accepted` is inherently lossy unless you define it clearly (e.g. “aggregate is no longer `unknown`/`pre_transit` only” vs “we saw an acceptance-class event in details”).

Gaps vs current usage (recommended additions):

1. `is_return_to_sender` (or a single `is_exception` if you want fewer fields)  
    `return_to_sender`, `failure`, and `error` are not `cancelled`, but they are exception-like in `process_event`. If you only have `is_cancelled`, you cannot distinguish “cancelled” vs “RTS / failure / error” without overloading `is_cancelled` (bad).
    
2. `is_available_for_pickup` (optional)  
    EP maps this to `transit`, not delivery. If product cares about “pick up at PO” vs “out for delivery”, a boolean helps; otherwise you can infer from normalized status enum only.
    
3. `is_out_for_delivery` (optional)  
    Same idea: last-mile signal without `delivered`.
    

If you want minimal expansion: add at least `is_return_to_sender` and treat `failure` + `error` as `is_exception` (one flag), and keep `is_cancelled` only for `cancelled`.
```
