## Alternative 1 — Minimal: factory method + reuse `SFTPReadersClient` (no new reader class)

**Idea**: Add PayPal SFTP settings (host, user, password or key, port) to `[Settings](monocle_integrations/_adapters/_settings.py)` and secrets/localstack wiring (mirror `ftp_llas_*`). Extend `[SFTPReadersClientFactory](monocle_integrations/_adapters/_sftp_readers/_sftp_readers_client_factory.py)` with `get_for_paypal()` returning a configured `SFTPReadersClient`.

**Selection logic**: Implemented **outside** the adapter (scheduled job / use case): `with factory.get_for_paypal() as client: ...` → `async for name in client.get_file_paths("ppreports/outgoing")` → filter `STL-(\d{8})\.\d+\.\d+\.CSV` (case-normalize as needed) → compute target date = “yesterday” in **configurable TZ** (Settings, e.g. `paypal_sftp_settlement_timezone`) → pick the single best match (if multiple for same date, define tie-break: lexicographic max on full name, or parse `.xx.xxx` segments).

**Pros**: Smallest diff; matches how LMS SFTP is exposed today; clear separation—adapter = transport, domain = rules.

**Cons**: Every consumer duplicates listing/filtering unless you later extract a shared helper.

---

## Alternative 2 — PayPal-specific thin adapter (single responsibility: “get yesterday’s STL”)

**Idea**: New class under `monocle_integrations/_adapters/_sftp_readers/` (or `_paypal/`) e.g. `PayPalSftpSettlementFileRetriever` that **depends on** `SFTPReadersClient` (constructed with PayPal creds) and exposes one or two methods:

- `async def fetch_previous_day_settlement(self) -> tuple[bytes, str]` (content + remote filename), or
    
- `async def resolve_previous_day_path(self) -> str` + reuse `get_file_contents` for clarity.
    

Internally: same listing + regex + TZ + tie-break as Alt 1, but **encapsulated** so callers do not reimplement PayPal rules.

**Pros**: Adapter boundary matches the product language (“retrieve previous day settlement”); easy to unit-test selection without mocking paramiko at every call site; still no S3/Oracle coupling.

**Cons**: Slightly more code than Alt 1; if PayPal adds multiple report types later, you may generalize or split.

---

## Alternative 3 — Hexagonal port + SFTP implementation (domain interface, infra adapter)

**Idea**: Define a small domain port (e.g. `PayPalSettlementFileRetriever` ABC) in `monocle_integrations/_domain/_ports/` with a method like `async def get_previous_day_settlement() -> PayPalSettlementFile` (bytes + metadata). Provide `PayPalSettlementFileRetrieverSftp` in adapters that uses `SFTPReadersClient` internally.

**Pros**: Best alignment with “hexagonal” and testability in domain layer; orchestrations depend on the port, not paramiko; swapping to PayPal REST or a mock in tests is trivial.

**Cons**: Most files touched for a purely internal feature; worthwhile if multiple entry points (CLI, scheduler, API) will call the same retrieval.

---

## Recommendation (if you must pick one)

- For **fast delivery** and consistency with LMS: **Alternative 1**.
    
- For **clear “adapter” product boundary** and fewer copy-paste bugs in selection logic: **Alternative 2**.
    
- For **long-term multi-consumer integrations**: **Alternative 3**.

## Configurable “yesterday” (your “unsure” → design choice)

- Add **Settings**: e.g. `paypal_sftp_settlement_timezone: str` (IANA name, default `UTC`).
    
- Compute calendar **previous day** in that zone, format `yyyymmdd`, filter STL files for that date.
    
- If the file for that date is **missing**, define behavior explicitly (raise `FileNotFoundError`-style domain error vs retry vs skip)—outside the adapter if using Alt 1.
    

---

## Tie-break when multiple files share the same `yyyymmdd`

PayPal’s example `STL-20260107.01.009.CSV` suggests batch/sequence segments. Document and implement one rule, e.g. **lexicographic max of full filename** (often matches “latest” if segments sort correctly) or **parse** `.(\d+)\.(\d+)` and compare tuples—prefer documenting PayPal’s semantics if available.
