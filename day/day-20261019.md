## Insights/Ideas
- 10:28 — A Drive sync alert full of weeks-old comments means the comments sidecar was rewritten (thread resolutions or doc re-upload), not new activity. Re-uploads re-source Word comments as Drive comments with new ids and strip assignment markers, so never key comments by id or raw body.
- 12:05 — The Drive comments API is not a ledger. Replies and resolve actions can lag the Docs UI per file for days (seen: 45h+ on the FSD; HTTP 200, `modifiedTime` still advances, exports stay fresh). The same client served another file's reply from 4 minutes later, so the lag is server-side per file, never the OAuth client. Google's guide scopes the API to Drive-level comments: "The Drive API treats this data as opaque and can't resolve internal document regions, cell coordinates, or slide elements." When the sidecar lags the UI, suspect the API, not the sync.
- 12:05 — Drive exports drop resolved comment threads. Verified twice: the FSD export lost a thread resolved that morning, and the money-services export dropped all 3 resolved threads. A downloaded file alone can never archive decisions.
- 12:05 — Comment-sidecar source split: open threads come from the fresh per-run docx/xlsx download, resolved threads from the Drive API. Exports drop resolved threads, so the two sets never overlap and no reconciliation key is needed. A thread resolved during an API freeze reappears (resolved, with its final replies) once the API catches up.
- 13:38 — Jira "not detecting the PRs"? Query `/rest/dev-status/latest/issue/summary?issueId=<internal id>` (JIRA_* creds in ioet/.env). It shows backend PR/branch/commit counts plus a per-entity `lastUpdated`, which separates a linkage gap (count 0) from an integration freeze (count fine, `lastUpdated` stale). The detail endpoint returns empty with OAuth-instance GitHub integrations — the summary endpoint is the reliable one.
