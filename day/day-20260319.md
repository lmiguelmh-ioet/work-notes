WMS-I-1006
“When the warehouse ships something, how do we tell enterprise systems exactly what was shipped, by whom, when, and in what package?”

- Transfer Order (TO): inventory moved between internal locations (lab/store/DC).
- Sales Order (SO): customer-facing order.
- Ship Confirm: final confirmation that goods actually left the building.
- Shipment / Shipment Line: header + line records in Oracle Shipping.

1. WMS generates XML shipment files every 15 minutes and drops them in Azure.
2. OIC polls Azure every X minutes, copies files to S3 inbound, and archives/moves source file.
3. OIC reads each shipment and branches by `Order Type`:
    - `TO` → process in Oracle
    - `SO` → process in Springfield, and sometimes also in Oracle (only if `SH.UDF6 = OMG`)
4. For SO shipments with tray IDs, generate/send LMS DST files.
5. Good records go to archive; bad records go to error folder + auto-create JIRA.

### 1) TO logic (Oracle)

For Transfer Orders, Oracle shipment generally already exists from pick confirmation step.  
Integration does:

- Find Oracle shipment lines by order number
- Update line shipped qty + tracking
- Update shipment carrier/mode/service
- Confirm shipment in Oracle

Result after confirm:

- Shipment lines become interfaced/shipped
- Shipment closes
- Packing slip finalized
  
### 2) SO logic (Springfield + Oracle subset)

All SO ship confirms go to Springfield in near real-time JSON over SNS/SQS.

But only SOs where `SH.UDF6 = OMG` are additionally processed in Oracle shipping APIs:

- Create shipment using WMS `ShipmentID` (newer requirement)
- Assign shipment lines to that shipment
- Update line-level shipped qty/tracking/serials
- Confirm shipment
  

### 3) Serial number rule

Important nuance from assumptions/changes:

- Serials expected from WMS for serial-controlled items
- For SOs, serial handling depends on packing condition described in scope notes
- Serials in ship confirm should match pick confirm serials, or operations need re-pick/re-ship process

### 4) Carrier mapping rule for Canadian TOs

When ship-to country is CA, WMS may send “manual” carrier-service values (prefixed `AManual...`) not directly valid in Oracle.  
So integration must use Oracle lookup `WP_WMS_CA_CARRIERS` to map:

- WMS carrier-service (`Meaning`)
- Oracle carrier (`Description`)
- Oracle service/mode (split from `Tag`, e.g. `GND-PARCEL`)
  
## Key Oracle API Sequence (for TO + eligible SO)

1. Get Shipment Lines (by order number)
2. Create Shipment (SO + `UDF6=OMG` only, shipment number from WMS)
3. Assign Lines to Shipment (SO + `UDF6=OMG` only)
4. Update Shipment Line (qty, tracking, serial range info)
5. Update Shipment Header (TO only: carrier/mode/service)
6. Confirm Shipment

If you get this sequence wrong, state transitions in Oracle will break.

The hardest parts are:

- Correct branching logic (`TO` vs `SO`, and `SO + UDF6=OMG`)
- Oracle API call ordering
- Carrier mapping via lookup
- Container→line matching for tracking/serials
- Robust exception routing and replay support
