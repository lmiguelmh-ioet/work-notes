### Design decisions (ours)

1. New dedicated UNION ALL arm in the PoD DM for the "Paid Expedite" line type — the only arm that emits expedite contract lines. No gate on the charge line's own state (fulfill status / `fulfilled_qty` / own-date): the charge line DOES have a fulfill record (probe 2026-11-20: TP51K801FZ line 3 CLOSED qty 1, undated detail; 82% of TEST expedite rows rest in `PAUSE FOR BILLING` qty 0), but emission keys off the regular lines' delivery plus the contract match, never the charge line's billing lifecycle. (Rewritten 2026-11-20: the original draft claimed the charge line has no fulfill records — false; and round-2 seat 2 showed a fulfill gate would couple emission to billing holds.)
2. PoD date = order-grain MIN over the order's REGULAR lines' per-line completion dates: `fulfill_delivery`'s per-line `MAX(actual_delivery_date)` for DELIVERY lines, `NVL(qc_fail_resolution.replacement_pickup_date, pickup_task_dates.pickup_completion_date)` per line on PICKUP_TASK orders (the standard arm's QC-fail redirect overlay). Regular = line types NOT IN (`WP_AI_WARRANTY`, `WP_PAID_EXPEDITE`, `WP_CPU_SHIP_ONLY`, `WP_SHIP_ONLY`); canceled lines per the standard-arm convention (exclude pre-fulfillment cancellations, keep cancel-after-terminal); MIN must be non-null; aggregation restricted to pool orders by `header_id`. Assumption (panel F7, unconfirmed): "first delivered" = first line to FINISH delivering (MIN of per-line MAX), the DM's own per-line dating convention. (Rewritten 2026-11-20 post-panel.)
3. PoD key uses the existing contract-line-combination fallback (`customer_contract_header_id || document_line_id`), as non-delivered pickup lines already do.
4. No `VRM_SOURCE_DOC_LINES` "U" record (U records are DEFERRED-split-only today).
5. Monocle orchestrator unchanged — it maps report rows through.
6. Base branch is the unmerged PoD DM stack tip `OTCM-153073-rmcs-i-3001-pod-canceled-covered-line` (`da8846cc`), live on dev1/stage — not `main`.
7. Functional questions posted as an FSD-thread reply, not Slack, and scoped to 3001 only — the billing-mirror question (3002) was deliberately routed out (user decisions 2026-11-19).
8. Proceeding assumptions recorded but NOT posted — restate at build start: item #3 only; documented sequence contract creation → billing → PoD; Satisfied Quantity = fulfilled quantity (1), Amount Applied blank; "first delivered" over regular product lines only; silent wait on never-delivered; returns don't change the expedite PoD. (Aruna's 2026-11-19 answers confirmed 3–6; item #3-only was superseded by her Q1 answer: any "Paid Expedite" line.)
9. DM line filter = `WP_PAID_EXPEDITE` line type (Aruna Q1, 2026-11-19), not item #3 only.
10. CPU orders are in scope (Aruna Q3): on CPU the "first delivered" date maps to the first regular line's pickup-task completion, the DM's existing CPU date source.
11. The expedite PoD row carries qty 1 and no amount; the $25 amount lives on the contract line created by 3003 (Aruna Q2).
12. RMCS-I-3003 is out of scope (user decision 2026-11-19): this ticket ships no contract-creation change, and the 3002 billing-mirror question is not pursued. The only open functional question is the PoD filter's item scope, which is 3001's own DM decision.

The PoD DM filter is FINAL: line type `WP_PAID_EXPEDITE` alone.

Emit contract binding the DM design (verified against the monocle reader 2026-11-20): the expedite row must be a PoD-only row — `SUB_LINE_ID` populated and every UPDATE-field column (UPDATE_RECORD_TYPE, DOCUMENT_ID, CONTRACT_END_DATE, …) blank. `_oracle_proof_of_delivery_reader.py` raises on update fields without UPDATE_RECORD_TYPE and on a missing SUB_LINE_ID for non-U rows, failing the whole report run.
